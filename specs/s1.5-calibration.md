## Problem Statement

S1 filled the spine, but every claim in it is still unverified. A user whose resume
says "React" and whose profile holds imported repos has no cheap way to convert
those claims into evidence — the trust ladder's corroboration currency (quizzes)
was split out and never built. Worse, the shipped recompute enforces no corroboration
cap, so repo-only evidence can already climb past the L3 the trust ladder promised.
The admin console's evidence panel renders its quiz-divergence slot empty, the
tuning loop it was built for has no quiz telemetry and no replay, and the generated
banks it must review have no review queue. And the distribution machine that turns
real work into authentic LinkedIn posts has no eligibility signal: nothing decides
what "a sizable portion done" means, so no draft can ever be grounded. Meanwhile a
user who spent real money on a Coursera certificate has nowhere to put it.

## Solution

Four calibrated surfaces over the shipped spine. **Quizzes:** per-skill
multiple-choice banks, generated lazily for all three bands at once, gated live by
a deterministic lint (admin spot-review runs after, asynchronously), graded
deterministically in a staircase session that settles the user's band in 5–10
minutes; retakes write SIGNED DELTAS through a narrowly opened negative lane in
the event service, so levels can fall honestly, grinding banks nothing, and a bad
morning can never touch non-quiz evidence. Taking quizzes is free and uncapped —
the cooldown is the only rate limit. **Certificates:** an allowlist of providers
with public verify URLs; submission fetches the public page, softly warns on name
mismatch, and writes externally anchored evidence decaying from the issue date;
off-list providers fall to plain claims with a quiz nudge. **Honesty machinery:**
the L3 corroboration cap becomes real inside the single-writer recompute —
single-source evidence clamps at L3 until a second source type corroborates.
**Console:** quiz telemetry (completion, drop-off, per-question success, retakes,
time per question) behind per-readout minimum samples so nothing renders as noise;
the evidence-vs-quiz divergence readout finally fills; a broken-question alert
feeds the bank spot-review queue; and the flag-gated what-if replay re-runs the
real event log under hypothetical weights — change → replay → diff → apply, where
apply is a guarded maintenance job, never a service-layer write. **Commit→post:**
post drafting unlocks from a stateless derived gate — user-authored pushed commits
since the last draft crossing a config threshold; the draft is generated from the
actual commit range and the user always edits, times, and posts it themselves.

## User Stories

**Quizzes**

1. As a signed-in user, I want to take a calibration quiz on any leaf skill in my
   profile or gap list, so that a claimed level becomes evidenced for free.
2. As the first user to take a quiz on a skill, I want its three banks generated
   without me waiting on any reviewer, so that lazy generation never walls me off.
3. As a user mid-quiz, I want a 6-question-round staircase that steps up when I'm
   doing well and down when I'm not, so that one session settles me at my real
   band without an interviewer.
4. As a user who self-assessed high, I want my session to start near my claimed
   level rather than at the bottom, so that I'm not insulted with warm-ups — and
   the staircase still corrects me if my claim was inflated.
5. As a user, I want the session hard-capped (18 questions), so that a rough day
   doesn't become an endurance test.
6. As a user finishing a quiz, I want to see my settled band and the exact points
   delta it wrote, so that the trust model stays visible at the moment it moves.
7. As a user who scored worse than last time, I want my score to fall honestly
   but bounded to quiz credit only, so that one bad morning can never erase my
   repo or work-experience evidence.
8. As a user, I want retakes to be free and uncapped, so that the only thing
   standing between me and a re-check is the 7-day cooldown.
9. As a user on cooldown, I want a clear "next retake" date, so that the gate is
   never a surprise.
10. As a user who abandons a quiz early, I want nothing recorded and no cooldown
    consumed, so that an accidental click costs nothing.

**Certificates**

11. As a user, I want to submit a certificate from an allowlisted provider with
    its verify URL, so that it counts as externally anchored evidence.
12. As a user, I want GLaDOS to fetch the public verify page and only warn on a
    name mismatch, so that nicknames don't block me but fraud isn't silent.
13. As a user submitting a certificate, I want to confirm the course→skill
    mapping before anything writes, so that points land on skills I actually
    earned.
14. As a user with an off-list provider certificate, I want it stored as a plain
    claim with a one-line quiz nudge, so that the path to verification is always
    shown and never forced.
15. As a user, I want my certificate evidence to decay from its issue date
    automatically, so that "certified long ago, forgot it" needs no special rule.

**Honesty machinery**

16. As a user whose only evidence is imported repos, I want my level to cap at
    L3 until a quiz or other second source corroborates it, so that the ladder
    actually means something.
17. As a user with unvalidated claims — from resume parse, work experience, or
    off-list certificates — I want quiz CTAs on the claim chips, so that I always
    see how to convert a claim into evidence.
18. As a visitor to the "how levels work" page, I want quizzes and certificates
    shown as the rungs they are, so that the ladder explains itself.

**Admin console**

19. As an admin, I want quiz telemetry — completion rate, drop-off question
    index, per-question success, retake frequency, time per question — behind
    per-readout minimum sample gates, so that I never tune from noise.
20. As an admin, I want the evidence-vs-quiz divergence readout to fill once
    quizzes exist, so that the population-level corroboration signal is visible.
21. As an admin, I want a question with enough answers and near-zero success
    auto-flagged into the spot-review queue, so that broken questions surface
    themselves.
22. As an admin, I want an async spot-review queue over lint-passed banks, so
    that publication is never blocked but bad banks can still be retired.
23. As an admin, I want change → replay → diff → apply over the real event log
    (flag-gated), so that weight changes show their blast radius before landing.
24. As an admin, I want replay APPLY to run as a guarded maintenance job, so
    that the per-event single-writer discipline is never violated.

**Commit→post**

25. As a user with a GitHub-linked project, I want post drafting to unlock when
    my authored pushed commits since my last draft cross a threshold, so that a
    milestone is real work, not a self-claim.
26. As a user who drafted but chose not to post, I want my commit counter to
    already be reset, so that every draft is backed by fresh real work.
27. As an eligible user, I want drafts grounded in my actual commit range (and
    my LinkedIn review's "what to post" advice), so that the post sounds like me
    and is honest.
28. As a user, I want to edit, time, and post the draft myself through
    LinkedIn's official share flow, so that posting is always my decision.
29. As a user whose project isn't GitHub-linked, I want the post surface simply
    absent, so that nothing promises something it can't ground.

## Integration

- **Event service (the load-bearing change):** `appendEvent` currently clamps
  every event to ≥0 points — the shipped code cannot write D59's negative
  deltas. S1.5 opens ONE narrow permission: `quiz_completed` (and only it) may
  carry a negative `pointsOverride`, already bounded by the caller; every other
  type keeps the seatbelt. The quiz service computes the bound before calling
  (delta ≥ − current DECAYED quiz-source contribution to that user+skill's
  score; uniform 90-day decay preserves the sign of the quiz-source sum, so a
  floor applied at write time holds at every read time). The single-writer path
  (`appendEvent` → `recomputeUserSkill`) is otherwise unchanged — S1.5 adds
  event types, one permission, and one clamp, never a second writer.
- **Corroboration cap ([D78a]):** `recomputeUserSkill` gains the D46(5) clamp —
  when a skill's evidenced events contain only cap-limited source types
  (repo/work-exp/certificate/quiz), the computed level clamps at L3; a second
  source type (e.g. quiz + imported repo) uncaps it. This is the enforcement
  S1 promised and never shipped; it lives in the single writer so every reader
  (gap map, recruiter filters, S2) inherits it.
- **Event vocabulary:** `quiz_completed` already exists (reserved in S0/S1) —
  S1.5 is its first real caller; payload = settled band, per-band correct/total,
  session id, bank version. NEW types: `certificate_added` (points from config,
  decay from issue date), `post_drafted` (audit only, 0 points; payload = project
  id + commit range — this event is the "since" anchor for the D74 gate).
  NO `project_milestone` type exists (D74: the gate is stateless).
- **Evidence readouts (D68):** the shipped `getAdminEvidenceReadouts` fills its
  `evidenceVsQuizDivergence` slot (currently an "until S1.5" note) from
  `user_skills` vs quiz-settled bands, and the admin page's Evidence-readouts
  section grows the telemetry headings (the page uses section headings, not
  tabs). Replay reuses the `runDecaySweep` bulk-rebuild pattern for APPLY.
- **Gateway:** S1.5 adds routed features on the shipped metered/cached path —
  `bank_gen`, `cert_course_map`, `post_draft` — each with routing-table +
  feature-flag rows (the `skill_definition` precedent). ROUTING SPLIT per
  [D78f]: shared-cache features (`bank_gen`, `cert_course_map`) are
  PLATFORM-route-only (a BYO user must never fund a shared asset);
  personal-output `post_draft` keeps BYO auto-win. All D4-cached where the
  output is content-addressed.
- **Storage module (D64):** certificate PDFs reuse the existing R2 adapter
  (put/get/signed URL/del), private bucket, short-lived signed URLs — same
  contract-test seam the resume PDFs use. Verify results cache on the
  certificate row itself (a public-page fetch is not a gateway call).
- **GitHub seam (D45/D67):** commit fetch reuses the live Clerk
  `getUserOauthAccessToken` token pattern from the import service — author-
  filtered per-repo commit listing (fork-safe by construction), nothing stored.
- **Parse seam:** certificate PDF text extraction (course name, dates) reuses
  the shipped unpdf text path; verification itself rides on the verify URL, not
  the PDF.
- **Work-experience entity (D56):** untouched mechanically, but its claim chips
  gain quiz CTAs (the D56 corroboration path: targeted quiz questions from the
  claimed skill's bank).
- **LinkedIn review (D53):** its cached "what to post" output feeds the draft
  generator's prompt — the review finally has its downstream consumer.
- **Config rows (D28 philosophy):** every dial named below is a config row
  (`quiz.*`, `telemetry.*`, `certs.providers`, `posts.*`) — rescaled at each D7
  ramp stage without a deploy; the D43/D47 console is the tuning surface.
- **S2 handoff:** quiz-settled bands join parsed claims as interview-adaptation
  inputs; the MCP quiz-delivery route (D56/D29) stays parked with S2.

## Implementation Decisions

**Quiz banks ([D41], [D59], [D70], [D78b–c])**: banks generate LAZILY — the
first take on a skill enqueues generation for ALL THREE bands (3 batched
`bank_gen` calls, ~24 questions each, grounded in the skill's definition field,
MCQs with difficulty/sub-topic tags); cached thereafter (key: skill + band + bank
version); an admin "generate now" button exists for demos/QA. PUBLISHING =
deterministic lint before live (no duplicate prompts, exactly one correct option,
tags present, option-count sane); lint failures regenerate once, then surface in
the admin queue. A lint-passed bank goes LIVE immediately — admin spot-review
runs asynchronously and retires a bad bank by publishing a replacement version
(old sessions keep their version reference). A feature flag can flip publishing
back to strict review-gating. Banks carry status
generating → live → retired. Leaf skills only (parent categories get no banks —
rollups aren't takeable).

**Staircase sessions ([D59], [D70], [D78d])**: bands = the shipped levels.bands
re-mapped L0–1 / L2–3 / L4–5. A session starts in the band matching the HIGHER
of the user's claimed/self-assessed level and evidenced level (placement hint
only — the claimed level never enters the score; default L0–1 when neither
exists), draws rounds of 6 questions from the current band's bank, and steps:
≥5 correct → up; ≤2 correct → down; otherwise settle. Hard cap 18 questions
(~5–10 min). Completion writes ONE `quiz_completed` event per skill with signed
delta points; the session and its per-question outcomes go to the telemetry
tables.

**Signed-delta retakes ([D59], [D76])**: the quiz service computes
`points = round(P_new − P_prev_raw)` where P = Σ per-correct weights by band
(`quiz.scoring` config). The negative is clamped so the DECAYED quiz-source
contribution to that skill's score lands at ≥ 0 — quiz credit can zero itself,
never go negative, never touch repo/work-exp/cert evidence. The first quiz on a
skill writes the full positive. Cooldown: per SKILL, rolling 7 days from a
completed session's end (`quiz.cooldownDays`). Abandoned sessions (< half the
first round answered) write nothing and consume no cooldown. Same-level retakes
write delta 0 by design — no refresh mechanism; staleness is honest (D76).
Taking quizzes is FREE and UNCAPTED in v1 ([D78e]) — no energy, no daily cap.

**Corroboration cap ([D46(5)], [D78a])**: inside `recomputeUserSkill`, after
scoring, classify the skill's evidenced events by source type; if every event is
a cap-limited type (repo / work experience / certificate / quiz), clamp the
band lookup at L3. Any second source type (S2 interviews, platform-guided
builds when they arrive) uncaps. Point values remain config-driven; the clamp
is structural, not a config dial (it is the trust ladder's promise, not a
tunable).

**Certificates ([D57], [D75])**: `certs.providers` config rows
`{slug, name, verifyPattern, exampleUrl}` seeded with the ~10 verifiable
providers (current URL shapes verified at build). Submission: provider + verify
URL required (allowlisted), PDF optional → storage module. Verification service:
match pattern → fetch the public page once (result cached on the certificate
row) → 200 + name-on-page soft match; mismatch = visible warning, never a gate;
fetch failure = unverified (resubmittable). Verified → `certificate_added`
evidence at the verified-cert ladder weight; off-list/unverified → claim-tier
storage with a quiz nudge (one line, never forced). Course→skills: one cached
`cert_course_map` call per course; the user CONFIRMS the mapped skills before
anything writes. `occurred_at` = issue date (verify page when present,
user-entered otherwise) — decay does the rest. PDF text fields (course name,
dates) via the existing unpdf path where present.

**Trust-teaching surfaces ([D62])**: claim chips on skills, work experiences,
and unverified certificates gain the quiz CTA ("verify with a 6-question check");
the "how levels work" page gains the quiz/certificate rungs with the user's own
profile as the worked example. One line per surface, linking to the central page.

**Telemetry ([D47], [D59], [D68], [D77])**: `quiz_sessions` + `quiz_answers`
record the journey (per-question outcomes, durations in ms; client-clock
telemetry, never evidence). Readouts render only above per-readout minimum
samples (config `telemetry.minimums`): per-question success ≥ ~20 answers per
question; completion ≥ ~10 sessions per bank; drop-off index ≥ ~20 sessions;
time per question ≥ ~50 answers; retake frequency over a 30-day window;
divergence (evidenced level vs quiz-settled band, per skill) only for skills
with ≥3 users holding both. ONE alert: ≥20 answers and <20% success → the
question auto-flags into the spot-review queue. Panels are aggregate-only.
Consumption = the D47 tuning sessions at each ramp stage (learner first, then
the D7 friend cohort).

**What-if replay ([D47], [D68])**: flag-gated console flow — admin edits
candidate weights (config-row drafts), replay re-runs the D24 computation over
the real event log with the hypothetical config (on-the-fly per request at ramp
scale; no persistence), and shows the level/score diff per skill — including the
corroboration clamp's effect — before any apply. APPLY = a guarded maintenance
job doing a bulk `user_skills` rebuild (the decay-sweep pattern) under the
hypothetical-now-real config — explicitly outside the per-event single-writer
path. Replay stays dark until real traffic exists (flag off at ship).

**Commit→post ([D22], [D40], [D74], [D78g])**: eligibility = GitHub-linked
project AND user-authored pushed commits on the linked repo since the last
`post_drafted` event (import date when none) ≥ `posts.minCommitsPerMilestone`
(default 10). Computed live at check time via the author-filtered commit
listing (same token pattern as import); nothing stored, no marker button.
Draft action (user-triggered only, ≤ `posts.maxPerWeek` = 2 per rolling week):
fetch the commit range, one `post_draft` gateway call grounded in commit
messages/diffs + project description + the cached LinkedIn-review "what to
post" output → 2–3 candidate drafts; user edits and posts via LinkedIn's
self-serve share flow (D22 guardrails: public repos or user-flagged work only).
Each draft action appends `post_drafted` (0 points) — resetting the eligibility
anchor even if the post never happens (the anti-spam ratchet; no honor-system
"posted" button). Non-GitHub projects show no post surface.

**Schema set (nothing more):** NEW tables `quiz_banks` (skill, band, version,
status, generatedAt), `quiz_questions` (bank, prompt, options JSON,
correctIndex, tags[]), `quiz_sessions` (user, skill, bankVersion, bandStart,
bandSettled, startedAt, endedAt, outcome, questionsAsked, correctCount),
`quiz_answers` (session, question, band, correct, ms, position), `certificates`
(user, provider, verifyUrl, verifiedAt, courseName, issuedOn, skills[],
storageKey?); NEW config rows `quiz.bands/roundSize/cap/stepUp/stepDown/
cooldownDays/abandonThreshold/scoring`, `telemetry.minimums`,
`telemetry.alertThreshold`, `certs.providers`, `posts.minCommitsPerMilestone`,
`posts.maxPerWeek`. ALTER: none — no existing table changes shape (the D74
stateless gate is why projects need no milestone column). Code changes in
existing services: the narrow negative permission in the events service, the
corroboration clamp in the levels service.

## Testing Decisions

- **A good test asserts external behavior through a seam** (CODING_STANDARDS):
  given spine state + an action, assert observable results — events written,
  `user_skills` moved, banks served, readouts rendered or correctly hidden —
  never internals.
- **Seam 1 (primary — everything): the service layer** against the shared
  embedded Postgres (S0/S1 global setup; `fileParallelism: false`; per-file
  cleanup of own rows). Every S1.5 service tested here: bank lifecycle +
  lazy generation, staircase state machine (step up/down/settle, cap, start-band
  placement), signed-delta math INCLUDING the decay edge (the January +16 →
  July-retake trace as a fixed-clock test), cooldown edges (per-skill blocking,
  abandoned session consuming nothing), certificate ladder (allowlist match,
  fetch-200 soft name warning, off-list → claim tier), corroboration cap
  (repo-only clamps at L3; quiz+repo uncaps; cap interacts correctly with
  decay), telemetry minimums (readouts hidden below N, rendered above), replay
  diff correctness, commit eligibility (author filter, since-last-draft anchor,
  threshold boundary, weekly cap).
- **The events-service negative lane gets its own focused tests:** only
  `quiz_completed` may go negative; other types still clamp; the bound floors
  the decayed quiz contribution at zero and never crosses sources.
- **Seam 2 (existing): the gateway adapter boundary** — `bank_gen`,
  `cert_course_map`, `post_draft` stubbed with deterministic JSON; D4 caching
  asserted at the service seam (same content → no second gateway call).
  Certificate verify fetches stubbed at the service boundary (no network).
- **Seam 3 (existing): the storage module contract tests** extended for
  certificate objects — same in-memory fake, no network.
- **Clock control:** delta/decay/cooldown tests run under injected fixed clocks
  (the decay math is the feature).
- Prior art: S1's 27 service-test files / 102 tests; the shared-Postgres rules
  in CODING_STANDARDS are non-negotiable.

## Out of Scope

- Observed-success calibration, weak-concept loops, FSRS anything (S4 study
  mode); adaptive per-user question selection beyond the deterministic
  staircase.
- Free-text "explain how it works" interview-style quizzes (staged later per
  D41); plugin/MCP quiz delivery (S2, D29/D56).
- Auto-posting to LinkedIn in any form — drafting only; posting is always the
  user's action (D40). Organization-page posting (partner-gated, D22).
- Issues/PRs-closed as an alternative milestone signal (parked config
  extension, D74); per-project milestone thresholds; milestones for non-GitHub
  projects.
- Certificate OCR (image-only PDFs), bulk cert import, provider badge display
  for unverifiable providers (D75).
- Alerts beyond the broken-question flag; email/Slack anything; per-user quiz
  leaderboards.
- Recruiter/e-portfolio surfaces (D11); the OQ7 rename checklist (fires before
  public marketing, unchanged).

## Further Notes

- Build-time verification items: CURRENT verify-URL shapes per seeded provider
  (D75 research, delegated); whether each verify page is server-rendered enough
  for a plain fetch (JS-rendered pages → treat as unverified + note); LinkedIn
  share flow copy; `bank_gen` prompt quality loop (lint pass rates; regenerate
  once then human review; the flag back to strict gating exists if rates are
  ugly).
- The friend-cohort math: 50 users × a handful of quizzes each reaches the
  ~20-answers-per-question minimums on popular skills within weeks — the
  telemetry gates are sized to light up during the first ramp stage, not after.
- Atria Dawn endpoint verification remains open from [D26]; the routing table
  keeps the swap cheap if it fails.
- The `post_drafted` anchor means the FIRST draft on a freshly imported repo
  counts commits since import — the eligibility service reads the
  `repo_imported` event's occurred_at as the baseline.
- The corroboration clamp will visibly LOWER some existing users' levels on
  first recompute after S1.5 ships — expected and honest (the ladder finally
  means what D46 said); the "how levels work" page is the explainer of record.
